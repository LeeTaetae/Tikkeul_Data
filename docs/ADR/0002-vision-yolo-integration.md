## 결정

### 1. 실행 위치: 기기 내(on-device)

서버 전송 방식은 채택하지 않는다. 이유:
- CLAUDE.md 보안 규칙 "카메라 원본 영상은 기본적으로 서버로 전송하지 않는다"와 정면 충돌
- ARCHITECTURE.md 설계 원칙 "네트워크 끊겨도 비전 경고는 동작해야 한다"와 불일치

`best.pt`를 Android는 TFLite(int8, NNAPI/GPU delegate), iOS는 CoreML(fp16)로 export해서 기기 내에서 추론한다. 입력 해상도는 640 대신 320~416으로 낮춰 연산량을 줄인다.

### 2. 화면 UX: 두 레이어로 분리

| 레이어 | 용도 | 기본 노출 |
|---|---|---|
| 라이브 탐지 오버레이 (박스+ROI 시각화) | 데모·신뢰 확인용, "지금 작동 중"을 보여줌 | 기본 OFF, 설정에서 토글 |
| 경고 배너 (`NavigationHazardAlert` 패턴 재사용) | 실제 주행 중 사용자에게 보이는 것 | 기본 ON |

카메라 방향은 핸드폰을 거치대(대시보드/윈드실드)에 꽂았을 때 자연히 앞유리 너머를 비추는 **전방(차량 진행 경로 앞쪽)**이다. "후면 카메라"는 핸드폰 뒷면 렌즈를 뜻하는 것이지, 차량 뒤쪽을 찍는다는 뜻이 아니다. 즉 이 기능은 후방 접근 경고가 아니라 **전방 돌발 장애물 경고**(킥보드 갑자기 도로 진입, 보행자 무단횡단, 동물 출현 등)다. ROI는 화면 하단-중앙의 사다리꼴 영역(차량이 실제로 지나갈 도로 경로)으로 잡고, 객체가 이 ROI에 걸치거나 박스 크기가 빠르게 커지면(=가까워짐) 단계를 올린다.

경고 배너는 새 디자인 없이 `NavigationHazardAlert.tsx`의 **시각 패턴**(색 띠, 아이콘 타일, stage pill, 닫기 버튼)을 그대로 따르는 별도의 작은 컴포넌트(`VisionHazardAlert.tsx`)로 만든다. 공용 `AlertType`(교통·ITS 경로 기반 경고 전용: accident/construction/congestion/school_zone/accident_prone)은 건드리지 않는다 — 비전 탐지 클래스(kickboard/motorcycle/vehicle/person/animal)를 여기 섞으면 `AlertFilter` 같은 무관한 교통 알림 목록 UI까지 새 타입을 떠안게 된다. 대신 `HazardClass`별 색·아이콘 매핑을 독립적으로 둔다. stage pill(`주의`/`접근 경고`/`최종 경고`)은 기존 `hazard.stage.*` i18n 키를 그대로 재사용한다.

**운전 중에는 카메라 화면 자체를 보여주지 않는다.** 주행 중 메인 화면은 평소 쓰는 내비게이션 지도이고, 그 위에 필요할 때만 경고 배너가 뜬다. 카메라+YOLO는 화면에 아무것도 띄우지 않고 백그라운드에서 탐지만 수행한다. 라이브 탐지 오버레이(위 표의 첫 번째 레이어)는 주행 중 기능이 아니라 정차 중·설정 화면에서만 켤 수 있는 별도 화면이다 — 운전 중 raw 영상을 띄우는 것 자체가 주의분산 위험이라 안전 앱 취지에 반한다.

**진동 트리거는 탐지(detection)가 아니라 ROI 진입/단계 상승(edge)에만 발생시킨다.** 같은 단계에 머무는 동안 재진동하지 않는다 — 기존 코드의 "단계가 바뀔 때만 TTS를 다시 읽는" 패턴과 동일.

### 3. 보호구역 상황 적응형 민감도

모델 재학습 없이 추론 파라미터만 상황별로 전환한다. CTX(상황판단) 모듈이 GPS 기준 보호구역/위험지역 진입을 감지하면:
- `person` 클래스 confidence threshold만 낮춤(기본 0.4~0.5 → 0.25). 다른 클래스는 그대로 둬서 오탐(동물·배경) 증가를 막는다.
- (선택) 추론 주기를 평소 5fps → 10fps로 올림
- (선택) ROI를 평소보다 넓게

### 4. 성능·발열 대비 (3단계)

1. **애초에 가볍게**: 저해상도 입력, 양자화 모델, 고정 저주기 추론, ROI만 크롭, 추론은 별도 워커 스레드
2. **느려지면 자동 저하**: 최근 추론 소요 시간을 측정해 목표 fps를 못 맞추면 fps/해상도를 자동으로 낮춤. 앱 최초 실행 시 짧은 벤치마크로 기기 성능 등급(상/중/하) 산정
3. **발열은 지연시간보다 먼저 감지**: iOS `ProcessInfo.thermalState` / Android 발열 API를 직접 모니터링. `serious` 단계에서 오버레이 렌더링 자동 OFF + fps 최소화, `critical` 단계에서 비전 추론 일시 중지 + `OfflineNotice`와 같은 톤의 배너("기기 발열로 전방 탐지가 잠시 멈췄어요") 노출. GPU/NPU delegate는 최대 성능이 아닌 저전력 우선 모드로 설정.

**비전 추론이 중단되어도 GPS 기반 교통·보호구역 경고(`NavigationHazardAlert`)는 독립적으로 계속 동작한다.** 비전은 보조 기능이며 전체 경고 시스템의 단일 장애점이 되지 않는다.

### 5. 설계 호출 (팀 확인 필요)

- **발열로 비전이 자동 중지된 상태를 사용자가 수동으로 다시 켤 수 있게 할지**: 기본값은 **불가** — 안전 기능이므로 OS가 기기가 식었다고 판단할 때까지 자동 재개만 허용한다. 이견 있으면 변경.

## 검토한 대안

| 대안 | 장점 | 채택하지 않은 이유 |
|---|---|---|
| 서버 추론(FastAPI + ultralytics) | 구현 단순, 기존 백엔드 스택 재사용 | 영상 비전송 원칙·오프라인 동작 원칙과 충돌 |
| 모든 클래스에 보호구역 민감도 적용 | 구현 단순 | person 외 클래스까지 낮추면 오탐 급증 → 경고 피로 |
| 탐지될 때마다 즉시 진동 | 구현 단순 | 멀리 지나가는 차량까지 매번 진동 → 사용성 저하, "위험 가능성"이 아닌 과잉 경보 |

## 영향과 위험

- mAP50-95 ≈ 0.44로 특히 recall(0.57)이 낮아 실제 주행에서 일부 객체를 놓칠 수 있다 — 경고 문구는 "탐지되지 않음 = 안전함"으로 읽히지 않게 작성해야 한다.
- 두 플랫폼(iOS CoreML / Android TFLite) export·검증을 동시에 진행해야 해서 vision-ai·frontend 작업량이 늘어난다.
- 기기 발열 자동 저하/중지 로직은 시뮬레이터로 검증 불가 — 실기기 장시간(30분+) 주행 테스트가 QA_TEST_PLAN에 필요하다.
- Expo Web 데모에서는 이 네이티브 파이프라인(TFLite/CoreML)이 동작하지 않는다 — 브라우저 테스트는 웹캠 입력 기반의 별도 경량 데모(예: TensorFlow.js)가 필요하며, 이는 실제 모바일 경로와 다른 코드다.

## 남은 작업 (담당 에이전트)

- `vision-ai`: best.pt → TFLite/CoreML export, 추론 래퍼(민감도 프로파일·발열 단계 연동)
- `frontend`: 오버레이 화면(토글), AlertType 확장, 진동 트리거 로직, 발열/성능 배너
- `architect`: ARCHITECTURE.md TBD 표 갱신
- `qa-tester`: 실기기 발열·장시간 주행 테스트 계획
